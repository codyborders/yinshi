# Yinshi Cross-Cutting Architecture Report

Scope is `backend/src/yinshi` (Python, FastAPI), `frontend/src` (React, Vite), `desktop/src` (Electron, TypeScript), and `sidecar/src` (Node). Vendored and build directories were excluded.

## 1. Noise IK and encryption protocol

There is no single authoritative definition. No shared schema, no IDL, and no generated artifact exist. The wire protocol is re-derived independently in Python and TypeScript. Matching literal constants are written twice.

The handshake layer duplicates every constant across the language boundary.

| Constant | Backend | Frontend |
| --- | --- | --- |
| Protocol name `Noise_IK_25519_ChaChaPoly_SHA256` | `backend/src/yinshi/services/runner_noise.py:22` | `frontend/src/crypto/noiseIk.ts:8` |
| Max message length 65535 | `backend/src/yinshi/services/runner_noise.py:26` | `frontend/src/crypto/noiseIk.ts:11` |
| IK first message overhead 96 | `backend/src/yinshi/services/runner_noise.py:24` | `frontend/src/crypto/noiseIk.ts:12` |
| IK second message minimum 48 | `backend/src/yinshi/services/runner_noise.py:25` | `frontend/src/crypto/noiseIk.ts:13` |
| Rehandshake threshold 1048576 | `backend/src/yinshi/services/runner_noise_session.py:24` | `frontend/src/crypto/noiseIk.ts:14`, `frontend/src/runner/encryptedRunnerClient.ts:398` |
| X25519 key length 32 | `backend/src/yinshi/services/runner_noise.py:23` | `frontend/src/crypto/noiseIk.ts:9` |
| Prologue and protocol tag `yinshi-runner-v1` | `backend/src/yinshi/services/runner_noise_session.py:23`, `backend/src/yinshi/services/runner_capabilities.py:27` | `frontend/src/runner/encryptedRunnerClient.ts:9`, applied at `:411` |

The two sides use different crypto stacks. Python uses `noiseprotocol` plus `cryptography` at `runner_noise.py:11-20`. The browser uses `@richardhopton/noise-c.wasm` at `noiseIk.ts:1-6`. Parity is maintained only by hand.

Capability tokens are issued and verified only in Python, at `backend/src/yinshi/services/runner_capabilities.py:161-306`. The Ed25519-signed claims are `scopes`, `token_id`, `transfer_id`, `expires_at`, `max_frame_bytes`, `max_session_bytes`, `initiator_public_key`, and `protocol`. The runner responder consumes them at `backend/src/yinshi/services/runner_noise_session.py:178-225`. It sends the handshake response payload `{"protocol":..., "transfer_id":...}` at `:216-224`. The frontend re-validates the same claim shape independently. See the `RunnerCapabilityResponse` interface at `frontend/src/runner/encryptedRunnerClient.ts:14-25` and `validateCapability` at `:118`. The handshake reply is parsed at `:449-452`.

The relay framing layer adds a 16-byte UUID prefix that only the Python endpoints understand. The hosted relay adds the prefix on client-to-runner traffic at `backend/src/yinshi/services/runner_relay.py:266-283`, as `uuid.UUID(transfer_id).bytes + ciphertext`. It strips the prefix on runner-to-client traffic at `:298-330`. The runner side parses and re-adds the same prefix at `backend/src/yinshi/services/runner_agent_relay.py:96-116`. Control messages are hand-built JSON strings rather than models. `backend/src/yinshi/services/runner_relay.py:262-263` and `:328-330` emit `'{"transfer_id":"..","type":"close"}'`. Those strings are parsed at `backend/src/yinshi/services/runner_agent_relay.py:77-95,129-156`. The browser never sees the prefix. It sends bare ciphertext and expects the literal readiness string `'{"type":"ready"}'` at `frontend/src/runner/encryptedRunnerClient.ts:441-443`.

The RPC envelope layer carries a version mismatch. The frontend request envelope sends `v: 2` at `frontend/src/runner/encryptedRunnerClient.ts:472-484`. The backend accepted key set is named `_REQUEST_KEYS_V1` at `backend/src/yinshi/services/runner_rpc.py:17` and lacks `query`. Version and type checks run at `:83-100`. The response envelope is built at `backend/src/yinshi/services/runner_rpc.py:313-325`. It is parsed independently at `frontend/src/runner/encryptedRunnerClient.ts:495-500`. Size limits diverge by construction. The browser caps a request at 49152 bytes at `encryptedRunnerClient.ts:487-488`. The responder caps the frame from the capability at `runner_noise_session.py:265-271`. The relay caps at `_RELAY_FRAME_BYTES_MAX` at `runner_relay.py:271`. The version-name mismatch and the missing `query` key are both open risks.

Desktop encryption is a separate, unrelated scheme. `desktop/src/runtimeSecrets.ts:6-11` defines `RuntimeSecrets {version:1, secretKey, encryptionPepper, keyEncryptionKey}` and passes those values to the Python helper. The backend reads them through settings. It derives keys with its own AES-GCM helpers at `backend/src/yinshi/services/crypto.py:48-231` and `backend/src/yinshi/services/control_encryption.py:11-30`. `desktop/src/diskEncryption.ts` only detects FileVault status through `detectFileVaultStatus`, imported at `desktop/src/main.ts:29`. It takes no part in the Noise protocol.

A protocol change requires coordinated edits in seventeen places. On the backend, `services/runner_noise.py` holds handshake primitives and length bounds. `services/runner_noise_session.py` holds the prologue, capability binding, handshake reply, and frame limits. `services/runner_capabilities.py` holds the protocol tag, claim schema, and scope set. `services/runner_rpc.py` holds the envelope, version, and route-to-scope table. `services/runner_relay.py` holds prefix framing, control JSON, and byte limits. `services/runner_agent_relay.py` holds runner-side demux. `api/runner_relay.py` holds the WebSocket endpoints. `api/runners.py` holds capability issuance, with the protocol echoed at `:198`. `runner_agent.py` holds the relay client, registration, and key pinning. `models.py` holds `RunnerCapabilityCreateIn:370`, `RunnerCapabilityOut:393`, `RunnerRegisterIn:324`, and `RunnerNoiseKeyConfirmationIn:360`. On the frontend the affected files are `crypto/noiseIk.ts`, `runner/encryptedRunnerClient.ts`, `runtime/runtimeTransport.ts`, `runtime/encryptedUpload.ts`, `runner/repositories.ts`, and `types/noise-c-wasm.d.ts`. Inside `runtime/runtimeTransport.ts` the relevant points are scope selection and the session byte budget at `:92`. Test mirrors also change. Those are `frontend/src/crypto/noiseIk.test.ts`, `frontend/src/runner/encryptedRunnerClient.test.ts`, and the backend suites for the five services above. Desktop is affected only when the `desktop/src/hostedApiGateway.ts` route allowlist must change. Section 3 covers that case.

## 3. Runtime abstraction and where the runtime decision is made

This is the key finding. Two orthogonal runtime axes exist, and they are not unified.

Axis A is the frontend `RuntimeRef.location`, with values `local`, `hosted`, and `byoc`. It is defined at `frontend/src/runtime/runtimeTransport.ts:10-17`. The unresolved variant sits at `frontend/src/runtime/runtimeRef.ts:6-13`. Axis B is the backend `AppMode`, with values `desktop`, `hosted`, and `worker`. It is selected in `backend/src/yinshi/main.py:415-457` through `create_app(mode=...)`. The names do not line up. Frontend `local` maps to backend `desktop`. Frontend `byoc` maps to backend `worker` inside `runner_agent`. Frontend `hosted` maps to backend `hosted`. Nothing in the code states or enforces that mapping.

The frontend branches on runtime in thirteen places. `frontend/src/runtime/useRuntimeResource.ts:42-51` is the canonical resolution. It parses the encoded ID, resolves the ref, and builds the transport. In `frontend/src/runtime/runtimeRef.ts`, `defaultRuntimeRef` at `:62-67` returns `local` on desktop and `hosted` elsewhere. `runtimeResourceId` at `:69-83` encodes the runtime into the URL as `hosted.`, `local.`, or `byoc.<b64url>.`. `parseRuntimeResourceId` at `:87-119` decodes it. `frontend/src/runtime/resolveRuntime.ts:20-45` resolves BYOC by fetching `/api/settings/runner` and requiring `noise_key_confirmed`. Three branches sit in `frontend/src/runtime/runtimeTransport.ts`. Lines `259-273` select `hostedApi` against `api` when the location is hosted and `window.yinshiDesktop` exists. Lines `286-296` dispatch BYOC requests through the encrypted Noise channel. Lines `322-340` branch uploads across BYOC encryption, the hosted bridge, and plain multipart. `frontend/src/runtime/promptStream.ts:174` sets the poll delay by runtime location. `frontend/src/api/client.ts:321-325, 374-378, 402-410` routes to the bridge using the hard-coded `DESKTOP_HOSTED_RUNNER_PATHS` set. That route bypasses `RuntimeRef` entirely. `frontend/src/api/piCommandsCache.ts:22` namespaces the cache key by runtime. `frontend/src/components/Sidebar.tsx:172-247, 269, 514, 973, 1096, 1132, 1161` discovers and aggregates all three locations. It rebuilds the default runtime at `:172-174` instead of calling `defaultRuntimeRef`. `frontend/src/pages/Settings.tsx:604-606, 631-638, 697, 716, 757-764` holds a third open-coded copy of that rule at `:604-606` and `:697`.

The backend branches on mode in twelve places. `backend/src/yinshi/main.py:415-424` validates the mode inside `create_app`. Worker mode uses a distinct middleware stack and returns early at `:309-322`. Desktop mode injects `DesktopTenantMiddleware` with the fixed `desktop-local` tenant at `:344-352`. Desktop mode also uses a different content security policy at `:361-363`. `_include_routes` at `:379-412` splits execution routers from control routers. Only hosted mode receives auth, runners, the relay, GitHub, and desktop devices. Hosted-only startup work runs at `:266`. The runner agent builds `create_app(mode="worker", ...)` in-process at `backend/src/yinshi/runner_worker.py:264-293`. `WorkerHttpDispatcher` at `backend/src/yinshi/worker_runtime.py:29-40` asserts `app.state.mode == "worker"` and dispatches over ASGI with no socket. An execution-time branch sits at `backend/src/yinshi/api/terminal_channels.py:97-105`. With no sidecar socket path it uses the settings socket and the host workspace path. Otherwise it remaps the path into the container. The mechanism behind that branch is `TenantSidecarContext` with a nullable `socket_path` at `backend/src/yinshi/services/sidecar_runtime.py:30-38`. A separate desktop terminal WebSocket proxy runs at `backend/src/yinshi/api/terminals.py:188-274`, parallel to the polling channel API. The route-to-scope table at `backend/src/yinshi/services/runner_rpc.py:132-215` gates what a BYOC runtime may execute.

Desktop branches in four places. `desktop/src/main.ts:369` and `desktop/src/runtimeLaunchConfig.ts:120-160` set helper and sidecar socket paths and environment. `desktop/src/localRuntime.ts:15-30` asserts that helper and sidecar agree on `SIDECAR_SOCKET_PATH` before starting the pair. `desktop/src/hostedApiGateway.ts:16-170` allowlists hosted API routes reachable through the bridge. That is the third copy of the route table. `desktop/src/helperSupervisor.ts` and `desktop/src/sidecarSupervisor.ts`, imported at `desktop/src/main.ts:32,48`, own process lifecycle.

The sidecar branches in three places, none about runtime kind. `sidecar/src/sidecar.js:937` reads the socket path from `SIDECAR_SOCKET_PATH`. Line `946` toggles dotenv on `SIDECAR_LOAD_DOTENV === "1"`, and desktop sets `"0"` at `desktop/src/runtimeLaunchConfig.ts:158`. Lines `1154-1210` hold one message-type dispatch table. The sidecar is runtime-agnostic.

The same URL surface is enumerated three times, in three languages, for three purposes. `backend/src/yinshi/services/runner_rpc.py:132-215` performs authoritative server-side scope enforcement. `frontend/src/runtime/runtimeTransport.ts:46-206` performs client-side scope selection for capability requests. `desktop/src/hostedApiGateway.ts:16-170` performs Electron bridge allowlisting. Any new API route requires edits in all three files plus the FastAPI router. Divergence here is a security-relevant defect class.

## 4. Terminal and agent-stream data paths

The polling terminal channel is required for BYOC and crosses twelve hops. `frontend/src/runtime/terminalChannel.ts:82` posts to `/api/workspaces/{id}/terminals` and polls `/events/{sequence}`, validating events at `:4-9,47-59`. `frontend/src/runtime/runtimeTransport.ts:286-296` wraps each BYOC call in a Noise RPC. `frontend/src/runner/encryptedRunnerClient.ts:441-520` performs the handshake and encrypted request. `backend/src/yinshi/api/runner_relay.py` and `backend/src/yinshi/services/runner_relay.py:266-330` relay UUID-prefixed frames. `backend/src/yinshi/services/runner_agent_relay.py:96-116` demuxes to the per-transfer session. `backend/src/yinshi/services/runner_rpc.py:71-325` parses the envelope, checks scope, and builds the response. `backend/src/yinshi/worker_runtime.py:29` dispatches into the worker app over ASGI. `backend/src/yinshi/api/terminal_channels.py:121-250` holds the terminal routes, and `:79-110` resolves workspace paths and the sidecar socket. `backend/src/yinshi/services/terminal_journal.py:85-512` writes newline-delimited JSON to the sidecar socket. It buffers output into sequenced batches at `_append_event:404`, `_split_terminal_data:439`, and `_decode_message:512`. `sidecar/src/sidecar.js:1184-1210` dispatches the terminal message types. `sidecar/src/sidecar.js:982-1082` spawns the pty. `onData` emits `terminal_data` at `:999-1003`, `onExit` emits `terminal_exit` at `:1005-1012`, and ready emits `terminal_ready` at `:1036-1042`.

A second terminal path exists as a direct WebSocket proxy. `backend/src/yinshi/api/terminals.py:273-274` exposes `/api/workspaces/{id}/terminal`. It carries its own sidecar framing helpers at `_send_sidecar:72`, `_read_sidecar:81`, `_proxy_browser_to_sidecar:92`, `_proxy_sidecar_to_browser:169`, and `_run_desktop_terminal_proxy:188`. Workspace resolution runs at `backend/src/yinshi/services/desktop_terminal.py:37`. Sidecar newline-JSON framing therefore exists twice inside the backend, at `terminals.py:72-91` and `terminal_journal.py:478-512`. Terminal event validation exists in Python at `terminal_journal.py:404-454` and again in TypeScript at `terminalChannel.ts:47-59`. The size bounds of 2 to 500 appear at `terminal_channels.py:37-38,49-51` and `terminalChannel.ts:38-45`.

The agent stream also has two paths. The SSE path starts at `frontend/src/hooks/useAgentStream.ts:127-133`, which calls `streamPrompt`. That function posts to `/api/sessions/{id}/prompt` at `frontend/src/api/client.ts:514-570`. Manual SSE line splitting runs at `:551-566`, and `normalizeEvent` runs at `:503-512`. The backend handles `prompt_session` at `backend/src/yinshi/api/stream.py:771-773`, with execution context resolved at `:630`. `backend/src/yinshi/services/sidecar.py:39-136` provides newline-JSON transport with an 8 MiB message limit. The sidecar dispatches `query`, `resolve`, and `cancel` at `sidecar/src/sidecar.js:1203-1209`, shaping content blocks at `:244-250`.

The polled run journal path starts at `frontend/src/hooks/useAgentStream.ts:114-126`, which calls `startRuntimePrompt`. `frontend/src/runtime/promptStream.ts:30-249` posts `/runs`, polls `/runs/{id}/events/{seq}`, and posts `/cancel`. It reuses `normalizeEvent` from `client.ts`. `backend/src/yinshi/api/prompt_runs.py:99-160` holds the routes. `backend/src/yinshi/services/prompt_journal.py:89-515` owns run lifecycle and sequenced batches. `_default_prompt_executor:58` bridges to the same sidecar execution as the SSE path, and remaining hops match. Across the two stream paths, event normalization is shared. Transport, status enums, cancellation, and terminal-status handling are written twice. Compare `client.ts:514-575` with `promptStream.ts:9-249`. Two journals with near-identical sequenced-batch semantics also exist, in `prompt_journal.py` and `terminal_journal.py`.

## 5. Component dependency map

In the frontend, `App.tsx` depends on the pages and `components/Sidebar`. `pages/Session.tsx:19,67` depends on `runtime/useRuntimeResource`. That module depends on `runtime/runtimeRef`, `runtime/resolveRuntime`, and `runtime/runtimeTransport`. `runtime/runtimeTransport.ts` depends on `api/client`, `runner/encryptedRunnerClient`, and `runtime/encryptedUpload`. `runner/encryptedRunnerClient.ts` depends on `crypto/noiseIk`, which loads noise-c.wasm. It also depends on `api/client` for capability issuance. `hooks/useAgentStream.ts` depends on both `api/client.streamPrompt` and `runtime/promptStream`. `components/Sidebar.tsx` depends on the runtime modules, `runner/repositories`, and `api/client`. `api/client.ts` depends on `window.yinshiDesktop`, typed in `types/desktop.d.ts`.

In desktop, `main.ts` depends on sixteen local modules, imported at `desktop/src/main.ts:21-48`. They cover app control, supervision, launch configuration, secrets, credentials, and disk status. They also cover the hosted gateway, hosted sessions, hosted auth, security, and shell policy. The rest are the auth callback listener, local repository import, automatic updates, and the IPC contract. `preload.ts` depends on `desktopApi` channel names and exposes `window.yinshiDesktop` at `desktop/src/preload.ts:11-30`. `helperSupervisor` spawns the backend in desktop mode through `backend/src/yinshi/desktop_runtime.py`. `sidecarSupervisor` spawns `sidecar/src/index.js` over `SIDECAR_SOCKET_PATH`.

In the backend, `main.py` depends on the `api` routers, middleware, `config`, and `db`. `api/stream.py` and `api/prompt_runs.py` depend on `services/prompt_journal`, which depends on `services/sidecar`. `api/terminal_channels.py` depends on `services/terminal_journal`, `services/workspace_runtime_paths`, `services/sidecar_runtime`, and `services/container`. `api/terminals.py` depends on `services/desktop_terminal` and talks to the sidecar socket directly. `api/runners.py` depends on `services/runners`, `services/runner_capabilities`, and `services/runner_relay`. `runner_agent.py` depends on `services/runner_agent_relay`. That module depends on `services/runner_rpc`, `services/runner_noise_session`, and `services/runner_noise`. `runner_agent.py` also depends on `runner_worker.py`, which imports `main.create_app` and `worker_runtime.WorkerHttpDispatcher`. `services/control_encryption` depends on `services/crypto`. In the sidecar, `index.js` depends on `sidecar.js`. That file depends on `git_auth.js`, `git_askpass_client.js`, and `constants.js`, with no dependency on any other component.

Eight couplings deserve attention. An import cycle is broken only by a deferred import. `backend/src/yinshi/runner_worker.py:264` imports `create_app` from `yinshi.main` inside a method body, while `main.py` reaches worker code through routers and `worker_auth`. The backend also imports itself across a network boundary. The BYOC runner runs a second full FastAPI app in-process at `runner_worker.py:288`. It calls that app over ASGI with no listening socket, in `worker_runtime.py`. One codebase acts as both control plane and remote worker, separated only by `app.state.mode`. Route knowledge is triplicated across three languages, as described in section 3. That is the highest-risk coupling in the repository. Two terminal subsystems and two agent-stream subsystems coexist with their own framing. `api/terminals.py` and `api/terminal_channels.py` both talk to the same sidecar through separately written newline-JSON helpers. `api/client.ts` bypasses the runtime abstraction. `DESKTOP_HOSTED_RUNNER_PATHS` at `client.ts:321-325` hard-codes three paths that must use the Electron bridge. A fourth control-plane path added later would silently take the wrong transport. The default-runtime rule is written three times, at `runtimeRef.ts:62-67`, `Sidebar.tsx:172-174`, and `Settings.tsx:604-606` plus `:697`. Terminology drifts across layers. The frontend says `local`, `hosted`, and `byoc`. The backend says `desktop`, `hosted`, and `worker`. Deployment material says runner, sidecar, and helper, and no file records the mapping. The sidecar is the only fully decoupled component. It knows nothing about runtimes, tenants, or Noise, and is a clean extraction boundary.

## Start here

Open `frontend/src/runtime/runtimeTransport.ts` first. Lines 10-17 define the `RuntimeRef` union that drives every frontend branch. Lines 46-206 hold the route-to-scope table. That table is duplicated in `backend/src/yinshi/services/runner_rpc.py:132-215` and `desktop/src/hostedApiGateway.ts:16-170`. Lines 259-340 contain the dispatch that selects plain HTTP, the Electron bridge, or the Noise channel. Read `backend/src/yinshi/main.py:379-412` next for the backend mode split.
