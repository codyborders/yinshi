# Code Review: Pi Autocompaction Persistence

## Summary

I reviewed the changes in `HEAD~1..HEAD`. The commit adds durable Pi JSONL session files, blocks transcript-only legacy sessions, forwards Pi compaction status to the browser, and cleans up Pi session files when workspaces are deleted.

One issue needs attention before this ships: workspace cleanup deletes a directory below an agent-writable home directory. If the agent replaces `.yinshi` with a symlink, deleting one workspace can remove another workspace's Pi session files. The rest of the change looks reasonable. I did not apply code changes during this review.

## Design Findings

### DESIGN-1: Pi session cleanup needs to own the filesystem safety check

Files: `backend/src/yinshi/services/sidecar_runtime.py:195`, `backend/src/yinshi/services/workspace.py:389`

The new design stores Pi context under the runtime home:

```text
<tenant-data>/runtime/workspaces/<workspace-id>/home/.yinshi/pi-sessions/<session-id>.jsonl
```

That location is useful because Pi can write to it from inside the sidecar container. It also means the agent can modify parent paths under `home`. The cleanup helper later deletes this directory:

```python
session_directory = os.path.join(home_path, *_PI_SESSION_DIRECTORY.split("/"))
if os.path.exists(session_directory):
    shutil.rmtree(session_directory)
```

`delete_workspace()` calls the helper and assumes the helper will only touch files owned by that workspace. The helper should enforce that assumption itself. Callers should not need to know which path segments are writable by the agent.

Move the path-safety rule into `delete_workspace_pi_sessions()`: refuse symlink parents, resolve the final directory, and delete only when the resolved path is the exact Pi session directory for the workspace being removed. If the check fails, log the cleanup refusal and leave the files behind.

A possible shape:

```python
home_path = Path(_workspace_home_path(tenant, workspace_id))
yinshi_dir = home_path / ".yinshi"
session_directory = yinshi_dir / "pi-sessions"

if yinshi_dir.is_symlink() or session_directory.is_symlink():
    raise ValueError("refusing to delete Pi session files through a symlink")

if session_directory.exists():
    shutil.rmtree(session_directory)
```

A stronger design would place Pi session files outside the agent-writable home and mount only that directory or file into the sidecar.

## Security Findings

### CRITICAL-1: Workspace deletion can follow an intermediate symlink and delete another workspace's Pi context

File: `backend/src/yinshi/services/sidecar_runtime.py:195`

The vulnerable operation is:

```python
home_path = _workspace_home_path(tenant, workspace_id)
session_directory = os.path.join(home_path, *_PI_SESSION_DIRECTORY.split("/"))
if os.path.exists(session_directory):
    shutil.rmtree(session_directory)
```

Here is the attack path. The sidecar runs with `/home/yinshi` mapped to the host workspace runtime home. A malicious prompt or compromised tool can replace `.yinshi` with a symlink:

```bash
rm -rf /home/yinshi/.yinshi
ln -s ../../bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb/home/.yinshi /home/yinshi/.yinshi
```

When the backend later deletes workspace `aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa`, this path:

```text
.../runtime/workspaces/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa/home/.yinshi/pi-sessions
```

can resolve to workspace `bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb` and remove its `pi-sessions` directory. Python will not recurse into a symlink when the final path is the symlink itself, but it can traverse a symlink in the middle of the path.

Impact:

- Deleting one workspace can delete another workspace's durable Pi JSONL files.
- Session continuity breaks because Pi loses the context it needs for resume and autocompaction.
- The JSONL files may contain sensitive model context, so cross-workspace deletion is also a data-boundary failure.

Required fix:

1. Check `.yinshi` and `pi-sessions` with `Path.is_symlink()` before deletion.
2. Resolve the directory and verify it still points to the workspace being deleted.
3. Add a regression test with two workspace homes and a symlinked `.yinshi` in the first home. After deleting the first workspace's Pi sessions, the second workspace's file must still exist.

## Performance Findings

No performance findings.

The new legacy-context check avoids extra database work for normal sessions:

```python
if _session_pi_context_version(session) >= 1:
    return
```

Only old sessions with `pi_context_version < 1` run the message-count query. The sidecar result delay also uses a single zero-delay timer around final-result emission. That adds constant work per prompt and is acceptable for this path.

## Code Quality Findings

### MAJOR-1: The cleanup test covers the normal directory case, but misses the hostile path case

File: `backend/tests/test_container.py:115`

Current test setup creates a normal directory:

```python
session_dir.mkdir(parents=True)
(session_dir / "session.jsonl").write_text("{}\n", encoding="utf-8")
keep_file = session_dir.parent / "keep.txt"
keep_file.write_text("keep", encoding="utf-8")
```

That proves the helper deletes `pi-sessions` and leaves sibling files under `.yinshi`. It does not protect the trust boundary introduced by this change: the agent can write under the runtime home.

Add a test that builds two workspace homes. In the first home, make `.yinshi` a symlink to the second home's `.yinshi`. Then call `delete_workspace_pi_sessions()` for the first workspace and assert the second workspace's JSONL file remains.

Sketch:

```python
first_home = data_dir / "runtime" / "workspaces" / first_id / "home"
second_sessions = (
    data_dir / "runtime" / "workspaces" / second_id / "home" / ".yinshi" / "pi-sessions"
)
second_sessions.mkdir(parents=True)
(second_sessions / "session.jsonl").write_text("{}\n", encoding="utf-8")

first_home.mkdir(parents=True)
(first_home / ".yinshi").symlink_to(f"../../{second_id}/home/.yinshi")

delete_workspace_pi_sessions(tenant, first_id)

assert (second_sessions / "session.jsonl").exists()
```

This test should fail before the fix and pass after the cleanup helper refuses symlink traversal.

## Simplification Findings

### MINOR-1: `piSessionFile` validation happens twice in the sidecar path

Files: `sidecar/src/sidecar.js:186`, `sidecar/src/sidecar.js:1611`, `sidecar/src/sidecar.js:1663`

`processWarmup()` and `processQuery()` normalize `options.piSessionFile` before calling `_createPiSession()`:

```javascript
const piSessionFile = normalizePiSessionFile(options.piSessionFile || null);
```

`_createPiSession()` then calls `openSessionManager()`, which normalizes the same value again:

```javascript
const normalizedSessionFile = normalizePiSessionFile(piSessionFile);
```

This is harmless, but it blurs which function owns path validation. Put validation at the filesystem boundary in `openSessionManager()`, and pass the raw option through from the callers. If `processQuery()` needs a comparison value before opening the session, create a small helper with a name that says it returns the normalized comparison key.

### MINOR-2: Workspace deletion hides cleanup dependencies inside the function body

File: `backend/src/yinshi/services/workspace.py:399`

`delete_workspace()` imports Pi cleanup helpers inside its tenant and non-tenant branches:

```python
if tenant is not None:
    from yinshi.services.sidecar_runtime import delete_workspace_pi_sessions
else:
    from yinshi.services.sidecar_runtime import delete_local_pi_session_file
```

If there is no import cycle, move these imports to the top of the module so reviewers can see that workspace deletion now owns Pi context cleanup. If a cycle exists, add a one-line comment above the local import explaining that constraint.
