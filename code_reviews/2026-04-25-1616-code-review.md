Branch: feature/byoc-runner

Target set: `backend/src/yinshi/runner_agent.py`, `backend/src/yinshi/services/runners.py`, `frontend/e2e/settings.spec.ts`, and `frontend/src/components/CloudRunnerSection.tsx`.

Phase 1 applied the `software-design` guidance to the diff and nearby code, with attention to shallow helpers, repeated policy knowledge, interface boundaries, and class-selection logic. I completed the same review passes manually from their documented rubrics.

## Summary

The diff is a focused cleanup. In Python, it deletes two one-line helper functions and lets each caller compute `explicit_storage_required` directly. In the frontend, it deletes one extra blank line from a Playwright spec and replaces status-class `if` chains with typed lookup tables.

The backend behavior is unchanged for the three current storage profiles. The direct boolean comparison is readable, but it moves a storage-profile policy rule into two call sites. The profile spec already owns storage defaults and validation facts, so the explicit-storage requirement would fit better there if this code keeps evolving.

The frontend lookup tables are an improvement for known status values because TypeScript can now require every `CloudRunnerStatus` key. One runtime fallback was lost during that cleanup: a server response with an unexpected runner status now produces `undefined` for the status badge classes. API JSON is not checked at runtime by TypeScript, so the badge helper should keep an offline-style fallback.

Severity summary: the design concern is the repeated AWS comparison in backend call sites; no security vulnerability was found; the major code-quality concern is the missing runtime fallback in `runnerStatusClass`; the minor simplification note is that `optionStatusClass` now only forwards to a constant map.

## Design Findings

### DESIGN-1: Put the explicit-storage requirement on `RunnerStorageProfileSpec`

Files: `backend/src/yinshi/runner_agent.py:204` and `backend/src/yinshi/services/runners.py:287`

Severity: DESIGN

#### What changed

Earlier code used named helpers for the policy:

```python
def _requires_explicit_storage(profile: RunnerStorageProfileSpec) -> bool:
    """Return whether a profile requires explicit Archil storage class evidence."""
    return profile.value != _AWS_STORAGE_PROFILE

explicit_storage_required = _requires_explicit_storage(profile)
```

The control-plane service had the same shape with a different helper name:

```python
def _profile_requires_explicit_storage(profile: RunnerStorageProfileSpec) -> bool:
    """Return whether a profile needs explicit Archil storage declarations."""
    return profile.value != _AWS_STORAGE_PROFILE

explicit_storage_required = _profile_requires_explicit_storage(profile)
```

The diff removes both helpers and leaves the comparison at each call site:

```python
explicit_storage_required = profile.value != _AWS_STORAGE_PROFILE
```

That deletion removes a shallow function. The remaining issue is ownership of the rule. A profile-level field would keep the policy next to the other profile metadata:

```python
@dataclass(frozen=True, slots=True)
class RunnerStorageProfileSpec:
    value: RunnerStorageProfile
    sqlite_storage: str
    shared_files_storage: str
    requires_explicit_storage: bool
    # existing fields stay here
```

Callers would then read the policy without knowing why it is true:

```python
explicit_storage_required = profile.requires_explicit_storage
```

#### How the code works

There are two copies of the storage-profile model because the runner agent and the control plane both validate storage facts.

`backend/src/yinshi/runner_agent.py` runs on the cloud runner. It reads environment variables, picks a storage profile, checks local directories, and sends capabilities to Yinshi.

`backend/src/yinshi/services/runners.py` runs in the control plane. It creates registration tokens, stores expected runner capabilities, validates the first registration payload, and validates later heartbeat payloads.

Each module defines `RunnerStorageProfileSpec`. A spec records the profile value, expected SQLite storage class, expected shared-files storage class, default paths, whether SQLite can live under shared files, and allowed storage classes.

The explicit-storage flow is:

1. Load or receive `storage_profile`.
2. Look up the matching `RunnerStorageProfileSpec`.
3. Compute whether explicit storage class values are required.
4. Validate `sqlite_storage` against the profile's allowed SQLite values.
5. Validate `shared_files_storage` against the profile's allowed shared-files values.
6. Reject missing or invalid storage values when the profile requires explicit values.

#### Why this matters

The removed helpers were shallow, so deleting them is a valid cleanup. A one-line helper can add an extra interface without hiding much complexity.

The remaining comparison still repeats domain knowledge in two modules: only the AWS profile may omit explicit storage class declarations. If a future profile needs a different rule, a developer must update both call sites and must remember that this comparison is part of storage policy. That is the design smell from the `software-design` pass: a rule that belongs to the profile spec has leaked into callers.

Moving the rule into `RunnerStorageProfileSpec` would make the profile interface deeper. Callers would ask the spec for a fact instead of re-deriving the policy from a profile name.

## Code Quality Findings

### MAJOR-1: Keep a runtime fallback for unknown runner statuses

File: `frontend/src/components/CloudRunnerSection.tsx:108`

Severity: MAJOR

#### What changed

The previous `runnerStatusClass` handled known statuses and returned the offline class for anything else:

```tsx
function runnerStatusClass(status: CloudRunnerStatus): string {
  if (status === "online") {
    return "border-green-500/40 bg-green-500/10 text-green-300";
  }
  if (status === "pending") {
    return "border-yellow-500/40 bg-yellow-500/10 text-yellow-200";
  }
  if (status === "revoked") {
    return "border-red-500/40 bg-red-500/10 text-red-300";
  }
  return "border-gray-600 bg-gray-800 text-gray-300";
}
```

The new version uses a map:

```tsx
const RUNNER_STATUS_CLASSES: Record<CloudRunnerStatus, string> = {
  offline: "border-gray-600 bg-gray-800 text-gray-300",
  online: "border-green-500/40 bg-green-500/10 text-green-300",
  pending: "border-yellow-500/40 bg-yellow-500/10 text-yellow-200",
  revoked: "border-red-500/40 bg-red-500/10 text-red-300",
};

function runnerStatusClass(status: CloudRunnerStatus): string {
  return RUNNER_STATUS_CLASSES[status];
}
```

The map is better for compile-time coverage of declared statuses. It should still return a default class when runtime data is outside that declared set. One compact fix is:

```tsx
function runnerStatusClass(status: string): string {
  return RUNNER_STATUS_CLASSES[status as CloudRunnerStatus] ?? RUNNER_STATUS_CLASSES.offline;
}
```

A stricter version validates the key before indexing:

```tsx
function isCloudRunnerStatus(value: string): value is CloudRunnerStatus {
  return Object.prototype.hasOwnProperty.call(RUNNER_STATUS_CLASSES, value);
}

function runnerStatusClass(status: string): string {
  if (isCloudRunnerStatus(status)) {
    return RUNNER_STATUS_CLASSES[status];
  }
  return RUNNER_STATUS_CLASSES.offline;
}
```

#### How the code works

`CloudRunnerSection` reads the runner through the API client:

```tsx
const loadedRunner = await api.get<CloudRunner | null>("/api/settings/runner");
```

The `<CloudRunner | null>` type parameter helps TypeScript check the rest of the file. It does not inspect the JSON response at runtime. If the backend sends a future value such as `"degraded"`, the browser still receives a plain string.

Rendering then follows this path:

1. `status` is set from `runner?.status`, with `"offline"` as the fallback when there is no runner.
2. JSX passes `status` into `runnerStatusClass(status)`.
3. The helper reads `RUNNER_STATUS_CLASSES[status]`.
4. JavaScript returns `undefined` when `status` is not a key in that object.
5. The badge loses its intended color classes even though the page still renders.

#### Why this matters

Network responses are a trust boundary for frontend code. A deployment mismatch, an older backend, or a newly added backend status can put values in the browser that the local TypeScript union does not list yet.

The old helper gave those values a readable offline-style badge. The map-based helper can keep its cleaner shape and still preserve that behavior by adding a fallback.

## Simplification Findings

### MINOR-1: `optionStatusClass` only forwards to a map

File: `frontend/src/components/CloudRunnerSection.tsx:112`

Severity: MINOR

#### What changed

The old helper encoded the two option statuses with an `if`:

```tsx
function optionStatusClass(status: RunnerSetupOption["status"]): string {
  if (status === "Experimental") {
    return "border-yellow-500/40 bg-yellow-500/10 text-yellow-200";
  }
  return "border-green-500/40 bg-green-500/10 text-green-300";
}
```

The new code stores the two classes in a typed map and keeps a helper:

```tsx
const OPTION_STATUS_CLASSES: Record<RunnerSetupOption["status"], string> = {
  Experimental: "border-yellow-500/40 bg-yellow-500/10 text-yellow-200",
  Supported: "border-green-500/40 bg-green-500/10 text-green-300",
};

function optionStatusClass(status: RunnerSetupOption["status"]): string {
  return OPTION_STATUS_CLASSES[status];
}
```

#### How the code works

`RUNNER_OPTIONS` is local static data. Every option has a status of `"Supported"` or `"Experimental"`. The option card renders a badge and calls `optionStatusClass(option.status)` to choose the class string.

Because the data is local and typed, this helper does not need the network-data fallback recommended for `runnerStatusClass`.

#### Why this matters

The typed map is clear and protects the code if a third option status is added later. The helper itself is now only a pass-through. If the team prefers fewer tiny functions, the JSX can use the map directly:

```tsx
${OPTION_STATUS_CLASSES[option.status]}
```

Keeping the helper is also reasonable because it gives the JSX a readable name and mirrors `runnerStatusClass`.
